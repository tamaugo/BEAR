What this deck is

One rate limit, six responses

Qwen’s provider returned HTTP 429 through every retry, so BEAR exported names from a cleaner built around Hyundai/i40.

This deck explains the cause, prices six neutral options for both setups and proposes a framework for every future BEAR change. No option is selected and nothing in BEAR has been changed.

A rate limit became messy names

BEAR · Issue 19Cause06 / 22

Cause · a second failure path

A successful response can still be unusable

HTTP 200 says the request arrived, not that the names are usable. The current code does not fully validate the shape, and some shapes can crash export.

1

names is not a map

{"names": ["Relay", "Starter motor"]}

A list or other type arrives where a map keyed by row ID is expected.

2

IDs are missing

{"names": {"101": "Relay"}}
// row 102 never answered

Some rows asked for in the batch have no entry, so they have no name.

3

Values are not strings

{"names": {"101": "Relay", "102": 42}}

A number, null or object where text belongs.

Illustrative payload shapes. Row IDs 101 and 102 are examples.

Every option must define

How the response type, expected IDs and string values are checked before names are accepted, how partial results are repaired row by row, and how an unresolved row appears to the operator.

Status of this validationProposed

Proposed, not implemented. It is required work under every option, including the ones that add a second model. It is not evidence that an option guarantees good names.

Cost · read with care

What the costs do and do not claim

BaselinesAssumed

The $0.05 and $0.037 totals are not itemised, so subtracting a Qwen cleanup is a modelling step. B and E assume the baseline holds one successful Qwen batch of Q. Twenty photos can yield fewer than twenty successful listings.

Recovery additionsUnknown

C, D and F add one extra call and give no credit for the failed primary. A pure 429 may not produce a billed completion; a timeout may be billed. Reconcile against actual usage instead of blindly adding.

Failed attemptsUnknown

BEAR’s local ledger records successes only, so it cannot establish what failed attempts cost. Failed-attempt and provenance instrumentation needs improvement before any reliability or savings claim.

Ledger observationVerified

On 8 October the ledger holds one Gemini clean_names success at $0.00060125, and Qwen successes at $0.00028666 and $0.00011514. It records no token counts and does not show exactly 20 names, so it is not a measured 20-photo price.

Output tokensAssumed

The code allows max_tokens=3000 today. If all 3,000 were billed, Gemini output alone would cost $0.0045. The 300-token figure is an assumption; billed reasoning and supported parameters need verifying.

Scope of the figuresUnpriced

Single-batch inference only: human review, implementation effort, hardware and funding or tax fees are unpriced. The figures are not spending ceilings, retry envelopes or probability forecasts.

BEAR · Issue 19Option A09 / 22
A

Improve the mechanical fallback

Framework fitDefine a tested local degradation path for optional output stages; critical photo reads and listing checks follow different failure rules.

Mechanism

Keep Qwen as primary. On an outage or invalid names, use a generic, vehicle-aware mechanical cleaner and mark the affected names for review.

Scope

Strip the job’s own vehicle words, known make, model and trim aliases, the exact part number and seller noise. Normalise punctuation and repeats. Keep component words and filename-side rules.

Pros

No extra model calls. The local fallback still works during provider outages. Behaviour is reproducible and easy to inspect.

Cons

Alias dictionaries need maintenance. Unfamiliar models can slip through, and broad stripping can remove useful component words. Rules alone cannot resolve ambiguous titles.

Verification before adoption

Fixtures for Shogun/Pajero, Corsa, Honda relays, Hyundai/i40, side codes and legitimate numeric component names. Flag empty or questionable names instead of inventing a component.

Latency and unknowns

No model round-trip, but the Qwen retry wait before fallback is unchanged unless a deadline is set (inference). Quality on unseen vehicles is unmeasured.

BEAR · Issue 19Option B10 / 22
B

Gemini as the primary name cleaner

Framework fitModel replacement is one configurable stage policy; approval rests on evidence and total-run cost, not token rates alone.

Mechanism

Replace the batch Qwen cleanup call with Gemini 3.1 Flash Lite. Validate the result, then use a generic mechanical fallback if Gemini fails.

Scope

Changes only title-to-name cleanup, in both setups. The reader and the Luna/Default photo-check selection stay independent.

Pros

Avoids the observed Qwen upstream bottleneck. Reuses a model already integrated in BEAR. Closed PR 18 reports clean examples on the affected job.

Cons

Gemini can also be unavailable. Using it for photos and names correlates failures. One successful job does not establish general naming quality.

Verification before adoption

Test JSON, ID and string validation; no invented components; preserve appropriate acronyms and seller component wording; forced Gemini outages. Confirm supported reasoning controls and actual billed tokens.

Latency and unknowns

Gemini latency against Qwen is unmeasured, and billed reasoning is unverified (max_tokens is 3,000 today). Cost figures use assumed token counts.

BEAR · Issue 19Option C11 / 22
C

Application-owned backup model

Framework fitExplicit per-stage adapters and budgets apply beyond names. Never use a Chat fallback directly for a Decisions call without a compatible contract and adapter.

Mechanism

Keep Qwen first. After eligible transient failures or invalid output, try Gemini. If both fail, finish with generic cleanup and a visible review status.

Scope

Define eligible errors and a bounded total deadline. Handle partial outputs per row and retry only unresolved names, without letting models alter other fields.

Pros

Normal-job Qwen cost and behaviour are preserved. BEAR can detect semantic and schema failures as well as API errors. A second model family adds a recovery path.

Cons

More policy and adapter code. Two models can both fail. Repeated successful-but-invalid answers can add charges and latency.

Verification before adoption

Force 429, network failure, malformed JSON, partial maps, wrong types and two-model failure. Validate every recovered row and preserve numbers, prices, URLs and images.

Latency and unknowns

Worst-case wait stacks a second model after the first fails, so the total deadline matters (inference). How often invalid-but-successful answers occur is unknown.

BEAR · Issue 19Option D12 / 22
D

OpenRouter’s managed model fallback

Framework fitA transport strategy inside the broader stage policy. Provider price filters constrain token rates, not the job’s total spending.

Mechanism

Send an ordered Qwen/Gemini models list through OpenRouter for API-level recovery. BEAR then applies its own schema and name validation and a generic local fallback.

Scope

Applies to compatible OpenRouter Chat requests. The fallback docs cover rate limits and provider failures; they do not validate BEAR’s part-name semantics.

Pros

Less custom API-error failover code. Gateway routing can recover within one client request. The model list and provider price limits are configurable.

Cons

Both choices still depend on OpenRouter. HTTP 200 with bad names needs BEAR handling. Provider or parameter filters can reduce availability; do not assume a second Qwen provider exists.

Verification before adoption

Check the actual returned model, provider and ledger usage. Test unsupported-parameter behaviour, malformed successful outputs and a full-gateway outage.

Latency and unknowns

BEAR sees a single call that may take longer (inference). Which model is billed on recovery must be reconciled from usage. Latency and fallback frequency are unmeasured.

BEAR · Issue 19Option E13 / 22
E

Mechanical first, escalate uncertain jobs

Framework fitCheap deterministic work comes before optional inference, only when its output contract and failure behaviour are safe for that stage.

Mechanism

Apply deterministic cleanup first. Call Gemini only when the result is uncertain; the cost illustration escalates the job’s complete title batch.

Scope

Use conservative acceptance rules and a maintained evaluation set. Acceptance is a heuristic, not proof that a component is correctly named.

Pros

Jobs accepted locally avoid a model call. Inference focuses on ambiguous cases. Simple titles can complete during outages.

Cons

A missed ambiguity silently hurts quality unless surfaced. More rules and evaluation work. Unseen vehicle words can fool the acceptance test.

Verification before adoption

Measure false acceptance, escalation frequency and name fidelity across makes before using any frequency for budgeting.

Latency and unknowns

Accepted jobs skip a call and escalated jobs add one (inference). The 20% escalation share is an assumption, not a claim that 20% of rows fail.

BEAR · Issue 19Option F14 / 22
F

Visible review and deferred repair

Framework fitReusable saved-stage resume and human review controls for degraded results, with stricter holds for critical uncertainty.

Mechanism

Expose affected rows and cleaning status, keep the paid lookup results, and let the operator approve manual names or rerun only cleanup later. Names can optionally be held until review.

Scope

A visible web and export warning plus an auditable repair record. A warning alone leaves names messy: this manages review, not automatic immediate cleanup.

Pros

Operators can see the degradation. The rest of the job is preserved. Stage-only replay avoids another full photo, read and lookup run.

Cons

Delays completion and needs attention; human labour is unpriced. Queue state, deduplication and safe atomic export replacement need building.

Verification before adoption

Verify review visibility, resume after restart, no duplicate billing from duplicate repair actions, and exact preservation of listing identity and filenames.

Latency and unknowns

Completion can wait on a person if names are held; replay timing is the operator’s choice. Reviewer time and review frequency are unknown.

Framework · steps 1 to 5 of 10

A framework for every future change

Setups
DefaultLuna / BetaExperimentalfuture setups
Stages
ChatDecisionseBaydeterministic processingexport
01

State the problem and evidence

Record a reproducible input, observed output, failure class and verified cause. Separate output quality from provider availability and listing identity. Mark what is measured, inferred, assumed or unknown.

02

Write the stage contract

List the fields a stage can produce, its validation rules, criticality and copy-through fields. Cosmetic names may be marked degraded. Photo-number uncertainty and a failed listing check must never become a guessed success.

03

Classify failures before recovery

Transient 429, 5xx and network faults permit bounded recovery. Invalid schema or meaning needs validation and selective repair. Auth or configuration errors, no credit and BEAR’s spend cap are terminal: never spend through another model.

04

Define each option in six or more lines

Mechanism, affected setups and stages, pros, cons, latency and quality evidence, cost for both baselines, uncertainty and a measurable verification plan. No preferred badge; combinations get a fresh combined cost.

05

Separate stage policy from model choice

Primary and backups, eligible errors, adapters, total deadline, per-attempt timeout, max attempts, concurrency, Retry-After handling and local degradation belong to a stage policy. Chat, Decisions and eBay need different adapters.

Failure classes at a glance

Transient429, 5xx, network: bounded recovery
Invalidbad schema or meaning: validate, repair rows
Terminalauth, config, credits, spend cap: stop
Criticalnever guess a part number or listing
Cosmeticmark degraded, show to the operator
BEAR · Issue 19Framework20 / 22

Framework · steps 6 to 10 of 10

Budgets, provenance and verification

06

Budget the entire run

Show normal, recovery and worst bounded-policy scenarios: rates, token assumptions, call counts, frequency, USD, percentage and multiple for each setup. Never multiply the whole photo run by a name-cleaner rate ratio.

07

Carry provenance to the operator

Save the actual model and provider, attempt count, fallback reason, usage, affected IDs and review status. Show meaningful warnings in results and the web page without exposing credentials. Keep unknown charges apart from confirmed zero-cost failures.

08

Resume the smallest failed stage

Keep source listing facts and paid results. Deduplicate and replace outputs atomically. Keep the four-field downstream row contract unless a reviewed schema change is chosen; attach diagnostics through compatible metadata.

09

Verify normal and degraded behaviour

Force outages, malformed, partial and non-string results, cap stops and unknown vehicle words. Test component-word preservation and filename-location rules. Check part numbers, prices, URLs and images are unchanged after name repair.

10

Consult, record, then implement through a PR

Record the chosen option or combination, quality tolerance, review behaviour, latency budget and recovery budget. Implement only after that. The owner merges; agents never change main directly or merge a PR.

Hard budget or soft estimate

Hard: before every attempt, reserve a conservative cost bound from bounded input and output volumes and the allowed rates. Reconcile concurrent reservations and possibly billed timeouts.

Soft: if those bounds cannot be enforced, call it an expected-cost estimate. A provider token-rate filter is not a job cap.
