## 3. Where we are stuck: the Mac live-run loop

The user clones `jev-integration` to `/Users/tamaugo/Desktop/BEAR WITH JEV/` and runs `BEAR` →
`/run-pipeline`. Four distinct failures have occurred **in sequence**; each was diagnosed and fixed
upstream, and the run was retried:

### Failure 1 — `/run-pipeline` missing; coordinator "reads all the files" ✅ FIXED
- **Cause:** `tools/bear.zsh` hard-coded `BEAR_HOME=/Users/tamaugo/Desktop/ebay-pipeline` (the old
  folder). On a fresh clone, pi launched from the wrong directory; pi only discovers project prompt
  templates from `<cwd>/.pi/prompts/`, so the command never registered and the coordinator ran with
  no instructions.
- **Fix:** `bear.zsh` now self-locates the repo from its own absolute path (`${(%):-%x}` + `:a`
  + `:h:h`), prints the resolved repo path in pre-flight, fails loudly if the harness is missing
  (`1ba1593`). User must also point `~/.zshrc`'s source line at the new folder.

### Failure 2 — subagent calls rejected in an infinite loop ("Provide exactly one mode") ✅ FIXED
- **Cause:** `run-pipeline.md` said *what* to delegate but never *how*. The coordinator invented a
  two-mode call (`agent`+`task` **and** a `tasks` array of `{photos, vehicle_string}` items). pi's
  subagent tool requires **exactly one mode** (single / parallel / chain) and counts them; every
  retry recomposed the same invalid call.
- **Fix:** verified the schema from pi's own extension source; Claude Code added a "How to
  delegate" section (canonical single-mode template + per-step task recipes for steps 1/4/7 —
  everything travels inside the `task` string, there are no other fields); plus a stop-looping rule
  (2 consecutive parameter rejections → report verbatim, never a third guess), "Sequential chain
  delegation" → "Sequential delegation", and the validator wired in as step 9 (`334aacb`).

### Failure 3 — Jev 401 "User not found" from Agent 1 🔶 FIX ON THE MAC (user-side action pending)
- **Diagnosis:** the same `.env` authenticates fine from the VM (smoke test passes, `$0.000014`,
  fresh request id) — so the Mac was sending a *different* string. User's own checks confirmed it:
  their shell printed `SET — SHADOWS .env` for `OPENROUTER_API_KEY` (a stale **shell export
  shadows** the good `.env`; `jev-core.ts` prefers the shell), and their `.env` holds a real,
  well-formed key (`sk-or-v…`, 73 chars — same key that passed live auth on the VM).
- **Fix upstream:** 401 errors now self-diagnose — `resolveApiKeyDetailed()` reports whether the
  key came from the shell (overriding `.env`) or from `.env`, describes it by shape only (first 7
  chars + length, never full material), flags the `.env.example` placeholder, and walks through the
  fix (`239eff0`).
- **Remaining user action:** delete the stale `export OPENROUTER_API_KEY=…` line (check
  `~/.zshrc`/`~/.zshenv`/`~/.zprofile`), or `unset OPENROUTER_API_KEY` / fresh terminal; then
  `printenv OPENROUTER_API_KEY` must print nothing.

### Failure 4 — pi refuses to load `jev-core.ts` ("does not export a valid factory function") ✅ FIXED
- **Cause:** pi auto-loads **every** `.ts` in `.pi/extensions/` and requires a default-exported
  factory function — helper libraries included. `jev-core.ts` (imported by `jev-decisions.ts`) had
  none. Found live on the Mac; the Mac had already produced the correct 4-line fix locally
  (`export default function (): void {}`), which was stashed to pull the 401 hardening — so it was
  landed upstream with a comment (`3cfd35f`). Node-based testing never caught this because only
  pi's loader enforces it.
- **Mac action:** `git stash drop` (discard the now-redundant local stub), `git pull`.

## 4. What we tried and why (decision trail)

- **Model selection by measurement, not vibes.** Every swap was A/B-tested live on the user's key
  against a 15-line hand-derived fixture. Contributor tiers were tested and *rejected* on floor
  stability (Agent 3 has **no failstate** — a bad row flows straight to the customer sheet, so
  worst-run floor beats average). qwen3.8-flash won (floor 12 vs incumbent 11) *before* prompt
  tuning; after tuning it hits 15.
- **"Bad rules vs bad model" hypothesis — confirmed and acted on.** Multiple different models
  failing the same fixture lines pointed at rules, not models. Fixture line 11 had carried a
  v3-era expectation (every model was under-charged ~1 line); the prompt's example lists were all
  single-position-word, so models over-generalized "strip the whole run". Three worked examples
  lifted qwen3.8-flash from 11 → 14/15, then to the 15/15 ceiling.
- **Residual failures moved to machinery, not more prose.** Sort flips, row-shift cascades, price
  floor/format slips are mechanically detectable and repairable — `agent3_validator.py` repairs
  what the rules define uniquely (re-sort, remap by unique part-number, price floor/format) and
  marks anything requiring judgment (exit 2 = stop before the spreadsheet). Loop converged:
  prompt fix → re-measure → validator → 15/15 on every scored run.
- **pi source read, not guessed.** Prompt-template discovery, the subagent tool's mode-counting
  rule, and the extension factory requirement were all verified in pi 0.87.1's source on the VM
  before writing fixes.
- **Claude Code (Opus/Sonnet via `opusplan`) used for all heavy code generation**, print-mode
  sessions, one discrete task per fresh session, `--allowedTools` scoped, costs logged to
  `/home/hermes/bear-jev/usage-log.jsonl` (~$4.46 across 10 sessions so far). The babysitter
  decomposes tasks, validates claims against empirical data before files change, and applies
  one-line fixes directly.
